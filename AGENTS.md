# AGENTS.md

This file gives coding agents the repository-specific context needed to make safe, focused changes to Autofile.

## Project Overview

Autofile is a self-hosted document management application composed of:

- `api/`: Rust 2024, Axum, Tokio, Diesel/Diesel Async, PostgreSQL, Apalis/Redis, and S3-compatible storage.
- `ui/`: React 19, TypeScript, Vite, PrimeReact/PrimeFlex, TanStack Query, and React Router.
- `docs/`: Zensical documentation published at `autofile.dev`.
- `charts/autofile/`: Helm chart with optional bundled CloudNativePG, Valkey, and RustFS services.
- `docker-compose.yml`: the complete local stack and the easiest way to run the application.

Read the root `README.md` and the documentation relevant to a change before editing behavior. The API reference in `docs/reference/api.md` is handwritten, not generated.

## General Rules

- Make the smallest change that fits the existing architecture and conventions.
- Keep API contracts, handwritten UI models, query hooks, and documentation synchronized.
- Preserve authentication checks, audit fields, database constraints, transactions, and asynchronous side effects when changing CRUD operations.
- Never add production secrets. Credentials in Compose and default chart values are development placeholders.
- Do not commit generated/local outputs such as `api/target/`, `ui/node_modules/`, `ui/dist/`, `site/`, `test-values.yaml`, `.envrc`, logs, or downloaded Helm dependency archives.
- The Docker build context is allowlisted by `.dockerignore`. Explicitly include any new file needed by an image build.
- There is no generated OpenAPI client. UI tests use Vitest (`npm test` from `ui/`). Do not invent generation or test commands that the repository does not provide.

## API Architecture

The API is mounted under `/api/v1` in `api/src/main.rs`.

- `api/src/api/`: Axum routes, request extraction and validation, authorization requirements, response shaping, and straightforward queries. Each resource module exposes `routes()`.
- `api/src/application/`: reusable business workflows, transactions, document processing, classification, indexing, and background-job handlers. Put multi-step behavior here rather than in HTTP handlers.
- `api/src/domain/`: Diesel models, changesets, API views, enums, and domain constants.
- `api/src/infrastructure/`: low-level integrations: S3 writes and deletes (`s3.rs`) and Redis/Apalis queue plumbing (`queue.rs`: storage constructors and the worker monitor).
- `api/src/shared/`: `AppState`, authentication, extractors, S3 response streaming, and focused helpers: `errors/{api,app,job}.rs`, `responses.rs`, `slugs.rs`, `serde.rs`, and `uploads.rs`.
- `api/src/schema.rs`: Diesel-generated schema. Migrations are the source of truth; do not edit this file independently.

Typical request flow is middleware -> `AuthUser` or `AdminUser` and `DbConn` extractors -> an `api` handler -> an `application` workflow for multi-step work -> Diesel/S3/Redis -> JSON, list, or streamed response.

Use `ApiError` (`api/src/shared/errors/api.rs`, re-exported from `api/src/shared/errors/mod.rs`) and the `AppErrorKind` mappings for HTTP failures. Error bodies use `{ "message": "..." }`. Authentication uses bearer access tokens and an HTTP-only refresh cookie. User management requires `AdminUser`; most resource routes require `AuthUser`.

Document and file mutations can trigger thumbnail creation, page extraction, OCR, classification, and index updates. Preserve those follow-up jobs and their ordering. Pay particular attention to consistency across PostgreSQL, S3, and Redis: existing workflows use transactions and cleanup paths where a single transaction cannot cover all three systems.

## Database Changes

- Add timestamped Diesel migrations under `api/migrations/` with `up.sql` and `down.sql`.
- Migrations are embedded in the binary and applied automatically at API startup.
- Prefer database constraints as well as request validation for durable invariants.
- Follow existing PostgreSQL conventions: `BIGINT` IDs, `TIMESTAMPTZ`, explicit foreign keys, composite keys for associations, and audit columns where applicable.
- Keep domain structs aligned with schema column types and order.
- Regenerate `api/src/schema.rs` with Diesel CLI after a schema change and review the result.
- Keep seed operations idempotent, normally with `ON CONFLICT`.

API integration tests live in `api/tests/`. They start a fresh `postgres:17-alpine` container and apply embedded migrations, so they require a working Docker-compatible daemon. They do not require the full Redis/S3 application environment.

## UI Architecture

Use Node.js 24 for UI development and CI.

- `ui/src/App.tsx`: application shell, provider composition, route table, and access guards.
- `ui/src/nav.ts`: primary navigation and breadcrumb metadata. Update it with route changes.
- `ui/src/pages/`: route-level list, create, edit, and detail screens.
- `ui/src/queries/`: TanStack Query reads and mutations. Keep server state here rather than fetching directly in pages.
- `ui/src/models/`: handwritten API models. They generally preserve backend snake_case field names.
- `ui/src/api.ts`: centralized authenticated request helpers and normalized `HttpError` handling.
- `ui/src/components/`: shared UI, including toast, confirmation, classifier, and document layout components.
- `ui/src/util/`: shared URL-state, slug-validation, and classifier-rule utilities.

Use `apiFetch`, `apiFetchList`, and `apiMutate` for JSON APIs, and `apiFetchRaw` for uploads, downloads, and blobs. These helpers supply credentials, bearer authentication, and a one-time refresh/retry after a 401.

Follow existing query-key and invalidation patterns in nearby `ui/src/queries/use*.ts` files. Resource lists generally keep paging, search, and sort state in the URL hash through `useHashListParams`; documents use a richer custom hash format.

PrimeReact is the widget library and PrimeFlex handles routine layout. Forms use `react-hook-form` and `Controller`; destructive actions use `confirmDialog`; feedback uses `AppToast`. Reuse `DocumentViewLayout` for document detail screens and slug utilities for slug-bearing resources. Keep layouts usable below the existing 900px responsive breakpoint.

Global styles live in `ui/src/App.scss`. Preserve the established `aut-`, `app-`, and `side-nav-` selector conventions and PrimeReact theme variables.

## Documentation And Deployment

- Add or move documentation pages in both `docs/` and the `nav` section of `mkdocs.yml`.
- Update `docs/reference/api.md` when endpoint paths, payloads, responses, authentication, or error behavior changes.
- Update concept, administration, or classifier YAML docs when changing user-visible semantics or configuration.
- Keep `charts/autofile/README.md` synchronized with chart values, credentials, requirements, and behavior.
- Validate both major Helm database modes conceptually. Offline rendering of the default CNPG mode needs `--api-versions postgresql.cnpg.io/v1/Cluster`.
- `make image` pushes images; do not use it as a routine local build check.
- Use `make version-bump` for patch releases or `VERSION=X.Y.Z make version-bump` for an explicit version. This keeps Cargo, npm, and chart versions synchronized and requires `yq`.
- Helm image tags default to `Chart.appVersion`; its leading `v` is intentional.

## Validation

Run checks relevant to the files changed. Prefer the full set for cross-layer work.

API checks from `api/`:

```bash
cargo fmt --all -- --check
cargo check --locked --all-targets
cargo clippy --locked --all-targets -- -D warnings
cargo nextest run --locked
```

`cargo nextest` is the canonical API test runner (install with `cargo install cargo-nextest`; CI installs it via `taiki-e/install-action`). It runs the same targets as `cargo test`, and CI appends a totals-only `## Rust Test Report` summary to the job summary.

UI checks from `ui/`:

```bash
npm ci
npm run lint
npm test
npm run build
```

`npm test` runs Vitest (`vitest run`), whose built-in `github-actions` reporter appends a `## Vitest Test Report` summary in CI.

`npm run build` includes TypeScript checking. `npm ci` is only needed when dependencies are not already installed or the lockfile changed.

Documentation checks from the repository root:

```bash
pip install -r requirements-docs.txt
zensical build --strict
```

Helm checks from the repository root:

```bash
helm lint charts/autofile --set database.mode=external --set database.url=postgres://user:pass@db:5432/autofile
helm template autofile charts/autofile --api-versions postgresql.cnpg.io/v1/Cluster
```

Compose configuration and full-stack smoke checks from the repository root:

```bash
docker compose config
docker compose up --build
curl --fail http://localhost:8000/api/v1/health/ready
```

Do not claim integration or smoke tests passed if Docker, external tools, or required services were unavailable. Report exactly which checks ran and which were skipped.
